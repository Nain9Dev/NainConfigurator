# Documentation Roadmap

Document version: 2.1  
Status: Active  
Last updated: 2026-07-28

## 1. Purpose

This roadmap records the documentation gates required before NainConfigurator is ready for implementation and, separately, before it is ready to process real customer data and support paying clients.

The objective is not to create documents for their own sake. Each artifact must remove a class of expensive implementation mistakes, preserve product scalability or make the commercial service operable.

## 2. Readiness levels

| Level | Meaning | Code or launch authority |
|---|---|---|
| Product foundation | Product, rules, logical data, contracts and flows agree | Documentation work only |
| Implementation ready | Commercial operating model, measurable quality requirements, architecture, physical data design, security, tests, operations and implementation plan are approved and the final review passes | Makes implementation eligible; a separate product-owner start authorization is required |
| Technical demo ready | Implemented MVP passes approved tests in a controlled environment | Does not authorize real personal data |
| Commercial launch ready | Privacy, retention, access, abuse protection, notifications, support and operations are approved and implemented | Authorizes onboarding paying clients |

Approval of one level does not imply approval of the next.

## 5. Gate B - Define the commercial operating model

Status: Completed on 2026-07-19.

Before architecture, the project needs a short commercial strategy artifact. Its decisions affect tenancy, branding, deployment, support and the cost of onboarding clients.

### Approved product-owner context

1. [x] **Initial paying customer:** Spanish small and mid-sized manufacturers and specialist retailers of configurable furniture.
2. [x] **Service model:** One shared multi-company SaaS service with strict company scope; dedicated deployment is deferred and cannot create a fork.
3. [x] **Revenue model:** Required setup/onboarding fee plus recurring subscription and separately scoped professional services.
4. [x] **Catalog operations:** Managed, validated and versioned publication by NainConfigurator during the MVP; no customer self-service administration yet.
5. [x] **Branding:** Constrained data-driven co-branding in the MVP; premium white-label may be added later without code forks.
6. [x] **Asset responsibility:** The customer owns accuracy and rights; NainConfigurator owns contracted preparation, technical validation and publication.
7. [x] **Lead handling:** The customer owns recipients, response and final offers; platform persistence alone is not notification.
8. [x] **Support promise:** Standard business-hours B2B technical support; exact targets are defined and costed in later gates.

### Approved starting model

- One shared multi-company SaaS product, with strict company-scoped data.
- Managed onboarding of company catalogs and 3D assets through a repeatable publication process during the MVP.
- A one-time onboarding/setup fee plus a recurring subscription.
- Configurable logo, colors and business identity without customer-specific code forks.
- A narrow first sales segment before expanding to more industries.
- Dedicated deployments only as a later premium option when justified by a paying customer.

The product owner approved this direction on 2026-07-19. Exact rates, quotas and contract terms remain commercial-launch inputs rather than implementation behavior.

## 10. Definition of documentation complete

NainConfigurator documentation is implementation-ready only when:

- All implementation-blocking documents are `Approved`.
- No blocking decision is hidden inside prose or marked unresolved.
- Business rules trace to data, API, flows and planned tests.
- The second-product acceptance proof is specified and no approved schema or contract requires a product-specific change.
- The commercial operating and tenancy model is approved.
- Performance, capacity and availability requirements are measurable.
- Privacy, retention, security and abuse controls have named owners.
- Architecture defines boundaries and transaction ownership.
- Physical database design implements, rather than reinterprets, the logical model.
- Test strategy covers correctness, concurrency, security and user recovery.
- Deployment, rollback, backup, monitoring and support are operationally defined.
- The implementation plan can be executed without inventing product behavior.

Commercial-launch documentation additionally requires approved legal content, quote-routing operations, client onboarding responsibilities and support commitments.
