# User Experience Requirements

Document version: 1.3  
Status: Approved  
Last updated: 2026-07-28  
Initial public locale: `es-ES`

## 1. Purpose

This document defines the observable public-user experience required for the NainConfigurator MVP. It turns approved product flows and commercial decisions into testable responsive, accessibility, degraded-rendering, branding, localization, form and recovery behavior.

Its scalability tests are:

> A fundamentally different second product must use the same interaction structure by loading different catalog data.

> A second company must apply its supported identity and default locale through data, without receiving a private client build or product-specific screen.

This document does not define visual mockups, CSS architecture, Babylon.js scene implementation, Blender asset composition, exact performance budgets, browser-version policy, analytics, physical database types or deployment topology.

## 3. Experience principles

1. **Commercial flow before rendering:** catalog selection, validation, saving and quote submission remain usable without 3D.
2. **Progressive enhancement:** capable devices receive the best supported visual experience without making weaker devices commercially unusable.
3. **Catalog-generated interaction:** groups, controls, labels, order, selection limits and compatibility guidance come from data.
4. **One supported client:** viewport, input mode, company branding or future white-label configuration never creates a customer-specific code branch.
5. **API authority made visible:** local price and rule guidance are identified as provisional until the API confirms them.
6. **Accessible by default:** accessibility is part of acceptance criteria, not a later presentation patch.
7. **Recovery preserves intent:** correctable errors retain safe user input and explain the next action without silent replacement.
8. **Privacy by interface:** personal data is collected only at quote submission and is not placed in share links, public codes or browser persistence.
9. **Locale-aware presentation:** human-readable text and money follow the resolved company locale; codes and decimal API values remain stable.
10. **Branding cannot reduce quality:** customer identity never overrides legibility, accessibility, security or required NainConfigurator service information.

## 4. Public experience scope

The approved public experience includes:

- Loading one company product from a stable launch context.
- Understanding the product, estimate disclaimer and current selectable groups.
- Selecting options using catalog-generated controls.
- Receiving compatibility guidance and authoritative validation results.
- Viewing an immediate local estimated price and a confirmed API estimate.
- Saving an immutable configuration and copying its reference or link.
- Retrieving a saved configuration without exposing quote contact data.
- Editing a saved selection as a new draft and saving a new configuration.
- Reading the active privacy resource and submitting a quote request.
- Recovering from network, catalog-version, privacy-version, validation and rendering failures.

Authentication, customer account history, payments, checkout, product browsing, customer administration and quote-status management remain outside the MVP.

## 5. Responsive and input requirements

### UX-RSP-001 - Complete commercial reflow

The complete commercial flow must work from a viewport width of 320 CSS pixels through supported large desktop widths without horizontal scrolling of text, forms, selection controls, price summaries or actions. A spatial 3D viewport may contain its own pan/rotate interaction, but it cannot force the surrounding document to scroll in two dimensions.

### UX-RSP-002 - No orientation dependency

The page must support portrait and landscape presentation and must not instruct the user to rotate the device to continue. Layout regions may reorder, stack or collapse without changing commercial state.

### UX-RSP-003 - Layout behavior, not device identity

Layout adapts to available space and capabilities rather than product code, company, user-agent brand or a fixed device list. Narrow presentation uses a readable single-column commercial flow. Wider presentation may place the visual viewport and commercial controls side by side while preserving the same logical reading and focus order.

### UX-RSP-004 - Zoom and text adaptation

Text resizing to 200 percent and page zoom/reflow equivalent to 400 percent must preserve content and operation. Fixed or sticky elements must not hide focused controls, messages, headings or primary actions.

### UX-RSP-005 - Equivalent input

Every commercial action must work with keyboard, pointer and touch where the platform supports those inputs. Dragging, multi-pointer gestures, hover or device motion cannot be the only method for an action. Camera manipulation may use gestures only when an equivalent non-drag mechanism or a non-3D path exists.

### UX-RSP-006 - Touch target policy

Selection controls and primary actions target at least 44 by 44 CSS pixels. Inline text links may use their natural text dimensions when sufficiently separated and when an equivalent accessible target is not needed.

Exact supported browser versions, device-performance classes and response-time budgets belong in `04.2-NonFunctionalRequirements.md`.

## 6. Accessibility requirements

### 6.1 Conformance target

The entire public web experience targets WCAG 2.2 Level AA, including responsive variants, loading states, errors, quote forms, the 3D region and its directly available equivalent presentation. Passing automated checks alone is not sufficient for a conformance claim.

This is a technical product target, not by itself a claim of compliance with every law applicable to a future customer.

### 6.2 Semantic structure

- Each page has one descriptive primary heading and a meaningful page title.
- Regions for product information, visual preview, option groups, price summary and quote form have programmatic names.
- Option groups use semantic grouping and labels; single-select and multi-select states expose name, role and value.
- Headings and DOM order follow the intended reading order even when CSS presents regions side by side.
- Images and meaningful visual assets have localized text alternatives; decorative assets are ignored by assistive technology.
- The document declares its resolved language on the root HTML element.

### 6.3 Keyboard and focus

- All interactive elements are reachable and operable using a keyboard without a trap.
- Focus order follows the logical task and does not jump into the 3D viewport automatically.
- Focus is always visibly indicated and is not obscured by sticky summaries or dialogs.
- Opening a modal moves focus into it, contains focus only while open, closes through an explicit action and returns focus to the triggering control.
- Ordinary price or selection updates do not steal focus.
- After submission with errors, focus moves to an error summary or the first invalid field according to the documented form pattern.

### 6.4 Color, contrast and motion

- Normal text meets at least 4.5:1 contrast and large text at least 3:1.
- Meaningful non-text boundaries, control states and focus indicators meet at least 3:1 against adjacent colors.
- Color is never the only indication of selection, availability, validity, price change or error.
- Content does not flash more than the applicable WCAG threshold.
- The client honors reduced-motion preferences by disabling non-essential camera motion, transition animation, parallax and automatic rotation.
- No visual animation starts merely because a product loads when reduced motion is requested.

### 6.5 Dynamic announcements

Meaningful asynchronous changes are exposed without unnecessary focus movement:

- Validation progress and completion.
- Authoritative price confirmation.
- Compatibility or selection-limit errors.
- Save success and copied-link confirmation.
- Quote-request persistence success.
- 3D degradation or unavailability when it changes the presented experience.

Rapid local price changes must be announced in a controlled way that does not produce a screen-reader message for every intermediate rendering frame.

### 6.6 Forms and cognitive clarity

- Every input has a persistent visible label; placeholder text is never the only label.
- Contact fields expose appropriate autocomplete purposes where supported.
- Required and optional status is expressed in text and programmatically.
- Instructions precede the relevant input or group.
- Error messages identify the problem and the correction, not only an error code.
- Previously entered safe values remain after a correctable validation or network error.
- The interface does not impose an avoidable time limit on configuration or quote completion.

## 7. 3D progressive-enhancement model

### 7.1 Rendering states

The visual region has explicit client states independent from the commercial draft:

| State | User-visible behavior | Commercial behavior |
|---|---|---|
| `NotStarted` | Product summary and controls may load before the renderer | Fully available when catalog is ready |
| `Loading` | Named progress or indeterminate loading message with an option to continue using controls | Fully available; selection changes are queued for visual application only |
| `Ready` | Interactive supported 3D presentation | Unchanged |
| `Reduced` | Lower-cost visuals, static camera or limited effects | Unchanged |
| `Unavailable` | Localized explanation and static/textual fallback | Unchanged; validation, save and quote remain available |
| `Failed` | Clear retry for the visual region and fallback presentation | Commercial draft and API state remain intact |

The renderer state is not persisted as commercial truth and cannot make a catalog-valid selection invalid.

### 7.2 Capability and failure behavior

- Rendering mode is selected from observed capability and runtime outcome, not only user-agent detection.
- Catalog controls must not wait indefinitely for the renderer to finish.
- The user may skip, stop or retry expensive visual loading without losing selections.
- A missing product or option asset identifies a presentation problem and uses an approved fallback resolved from the asset system.
- A failed visual update preserves the selected option and presents the selection textually.
- Saving may omit optional `visualState` when the visual region is unavailable; commercial selections remain identical.
- A saved configuration whose visual state is unsupported remains fully readable as a commercial snapshot.

### 7.3 Accessible visual description

The 3D region has a concise accessible name and text describing its current purpose. The selected configuration summary outside the canvas provides the authoritative accessible description of product choices, price and validation state. The user is never required to identify a finish, component or incompatibility only by inspecting the image.

## 8. Catalog-generated interaction

### 8.1 Product header

The product header presents, in the resolved locale:

- Company identity.
- Product name and description.
- Current estimated-price label and currency-formatted amount.
- Price disclaimer.
- Clear indication that the value is an estimate and whether it is locally calculated or API-confirmed.

Internal codes may appear in a details or reference context but cannot replace readable names.

### 8.2 Option groups

- Groups appear in catalog order and use their catalog name as the visible and programmatic group label.
- `maxSelections = 1` uses an accessible single-selection pattern.
- `maxSelections > 1` or null uses an accessible multiple-selection pattern.
- Minimum and finite maximum requirements are explained when they are not obvious.
- Each option exposes its name, selected state and formatted price effect.
- An explicit no-feature option remains a normal option when provided by catalog data.
- Disabled presentation cannot replace validation unless the client can explain the data-driven reason and the API still revalidates.
- A new product group requires no new screen component merely because its business name differs.

### 8.3 Price feedback

The local estimate updates responsively and remains labeled as provisional. An API-confirmed result is visually and programmatically distinguishable without relying only on color. Changing any selection removes the confirmed state until the API validates the new canonical selection.

## 9. Loading, empty, error and recovery states

### 9.1 Catalog loading

- Show a localized text status; skeletons or animation are optional presentation aids.
- Do not render fabricated default options before authoritative catalog data arrives.
- A slow state may explain that the product is still loading and later offer an explicit retry according to the non-functional timeout policy.

### 9.2 Product unavailable or not found

- Show a non-technical localized explanation and a safe retry when retry could later succeed.
- Do not expose whether an internal catalog defect, inactive state or authorization-sensitive record caused the public unavailable result.
- Never display another company's product as a fallback.

### 9.3 Validation errors

- Map stable API error codes to localized user guidance.
- Associate field/group errors with their affected control when possible and also provide a summary for submission failures.
- A compatibility error identifies the involved readable selections using catalog data.
- Unknown errors show a generic localized message and a `traceId` that can be copied for support; technical details remain hidden.

### 9.4 Catalog-version conflict

The interface reloads the catalog, preserves codes that still exist only as a proposed draft, explicitly identifies removed or changed choices and requires user review. No replacement is selected silently. The previous confirmed-price state is cleared.

### 9.5 Network uncertainty

During an uncertain create result, the related action is not treated as a fresh intent. The interface preserves the frozen payload and request ID, indicates that the result is being checked or retried, and prevents accidental rapid duplicate submission. A deliberate payload correction creates a new request ID as defined by FD-004.

## 10. Saved configuration experience

### 10.1 Successful save

The confirmation presents:

- Localized statement that the configuration was saved.
- Public configuration code.
- Estimated price and disclaimer.
- Copyable share link or equivalent copy-code fallback.
- Clear action to continue to quote request or return to editing as a new draft.

Copy or share success is visible and announced. Failure leaves the code visible for manual copying. The share payload contains no quote contact data.

### 10.2 Historical retrieval

The view identifies saved product, company, selections, price components, estimate, currency, creation time and configuration code from the immutable snapshot. It identifies that later catalog values may differ and does not imply current availability.

If the current product is unavailable, the view remains readable but the new-quote action is disabled with the approved explanation. Current branding may be presented when available; absence or later branding changes never rewrite snapshot content or block the view.

### 10.3 Editing after save

Changing a saved selection clearly marks the view as a new unsaved draft. The old code continues to identify the old snapshot. Saving creates and presents a new code, and a quote action must state which saved configuration it references.

## 11. Quote-request and privacy experience

### 11.1 Quote form

The form contains visible labels for required name and email, optional phone and message, and one unchecked explicit privacy-notice acknowledgment control. Contact data is not requested before the user enters the quote flow.

The active immutable policy resource is available before the checkbox, opens without discarding form state and is identified by readable link text. Acknowledgment is not preselected or inferred from continuing. The label does not claim marketing consent or select the controller's lawful basis.

### 11.2 Privacy-version change

When the active policy changes, the interface clears acknowledgment, presents the new policy resource, explains that review is required and requires a new explicit action. Other correct contact values may remain in the in-memory form.

### 11.3 Success wording

Successful quote creation uses wording equivalent to:

> Solicitud registrada. Referencia: {quoteRequestCode}.

It may explain that the company will handle the request, but it must not claim that an email was sent, an employee was notified, a response time is guaranteed or a binding quote exists.

After confirmed success, personal form values are cleared from the public client unless an approved accessibility need requires a short-lived in-memory confirmation. They are never written to the URL, share payload, general local storage or analytics.

## 12. Company branding requirements

### 12.1 Supported MVP profile

Each public company may have one versioned presentation profile containing:

- Branding mode: `CoBranded` in the MVP.
- Optional managed logo asset key.
- Primary semantic surface color in `#RRGGBB` form.
- Foreground color intended for content on that primary surface in `#RRGGBB` form.
- Positive branding version for cache and publication control.

Company display name remains the textual fallback and accessible identity. The MVP does not accept arbitrary CSS, JavaScript, HTML, fonts, layout definitions, per-product themes or customer-hosted executable assets.

### 12.2 Validation and fallback

- Branding pairs used for normal text must meet at least 4.5:1 contrast before publication.
- Other generated interactive states must retain applicable text, non-text and focus contrast.
- Missing or failed logos fall back to company name without blocking the product.
- Invalid, incomplete or unsupported branding falls back to the accessible NainConfigurator default theme and is logged for operators.
- Branding never changes selections, prices, snapshots or `catalogVersion`; its own version changes independently.
- Required legal, privacy, support and co-branding information cannot be hidden by a customer theme.

### 12.3 White-label boundary

White-label is not active in the MVP. A future `WhiteLabel` mode may change supported service identity surfaces through data, but cannot enable arbitrary code, remove mandatory notices, weaken accessibility or create a separate release.

## 13. Language and localization requirements

### 13.1 MVP locale policy

- The supported public MVP locale is `es-ES`.
- Each company has one `DefaultLocale` expressed as a BCP 47 language tag.
- A public company may be published only with a default locale supported by the client release.
- The initial product catalog, compatibility guidance, price disclaimer, privacy resource and public UI copy are presented in Spanish.
- Browser language does not silently override the company's published locale.
- The root HTML `lang` value matches the resolved locale; known fragments in another language declare their own language.

### 13.2 Internationalization boundary

All application-owned UI copy uses locale resources keyed by stable semantic identifiers. Product and company content comes from catalog/company data. Source code must not concatenate Spanish word order, currency symbols or product-specific labels into business behavior.

Adding another company that operates in one different supported locale must require locale resources and company/catalog data, not language-specific schema fields such as `NameEs` or `NameEn`.

Serving multiple simultaneous locales for the same company is outside the MVP. If approved later, it must use generic locale-keyed translations and explicit fallback rules rather than adding one column per language.

### 13.3 Historical locale

A saved configuration records the BCP 47 content locale used for its human-readable commercial snapshots. Retrieval declares and formats that snapshot using the stored locale even if the company later changes its default locale.

## 14. Currency and numeric presentation

- API money remains a decimal number plus ISO 4217 currency code; formatted strings are presentation only.
- The client uses locale-aware formatting. For `es-ES` and `EUR`, `819.90` is displayed according to Spanish conventions, for example `819,90 €`.
- Option adjustments indicate direction explicitly, such as `+35,00 €`; zero adjustments use a localized neutral label or `0,00 €` consistently.
- User-visible money always includes currency context and never relies only on a symbol when ambiguity is possible.
- Codes, request payloads and calculations never parse a localized displayed string back into authoritative money.
- The client does not perform independent tax, discount, shipping, installation or final-quote calculations.
- Estimated-price wording and the approved disclaimer remain adjacent or directly associated with the amount in every summary and confirmation.

## 15. Content and terminology policy

- Public copy uses plain Spanish and avoids internal concepts such as aggregate, idempotency, DTO or catalog defect.
- One concept uses one stable term across loading, configuring, saving and quote flows.
- Buttons describe outcomes: for example, `Validar configuración`, `Guardar configuración` and `Solicitar presupuesto` rather than ambiguous `Aceptar`.
- Destructive or state-changing actions explain consequences before confirmation when the consequence is not obvious.
- Error copy describes what the user can do next.
- Company-provided copy is reviewed during onboarding for accuracy, language and required length; client text overflow cannot be solved by truncating commercial meaning silently.

## 16. Acceptance scenarios

### UX-SC-001 - Second product uses the same controls

Given a product has different group names and selection limits from `DESK-001`  
When its valid catalog loads  
Then the same generic group controls, summary, validation, save and quote flow work without a product-specific screen.

### UX-SC-002 - Narrow viewport

Given a 320 CSS pixel viewport  
When the user completes the commercial flow  
Then readable content and controls reflow without document-level horizontal scrolling and without requiring 3D interaction.

### UX-SC-003 - Keyboard-only flow

Given the public page and a loaded catalog  
When the user operates only with a keyboard  
Then every selection, validation, save, privacy and quote action is reachable, visible in focus and operable without a trap.

### UX-SC-004 - Renderer fails

Given valid commercial catalog data and a renderer failure  
When the user configures and saves the product  
Then textual controls, validation, estimate and saving remain available and no selection changes because of the failure.

### UX-SC-005 - Reduced motion

Given the user requests reduced motion  
When the configurator loads and selections change  
Then non-essential automatic camera and transition motion remain disabled without reducing commercial functionality.

### UX-SC-006 - Invalid customer branding

Given branding data is missing, inaccessible or its logo fails  
When the product loads  
Then the accessible default theme and company-name fallback appear and the product remains commercially usable.

### UX-SC-007 - Spanish money

Given company locale `es-ES`, currency `EUR` and authoritative amount `819.90`  
When the client presents the estimate  
Then it uses Spanish locale formatting and never sends the formatted string back as price authority.

### UX-SC-008 - Catalog conflict review

Given a draft uses an older catalog  
When the API reports a version conflict  
Then the interface reloads, identifies preserved and removed selections, clears confirmed price and requires review before saving.

### UX-SC-009 - Accessible asynchronous price

Given a user of assistive technology changes a selection  
When local and authoritative prices update  
Then the confirmed status is exposed without stealing focus or announcing rendering-frame noise.

### UX-SC-010 - Saved configuration without current product

Given a historical configuration whose current product is unavailable  
When its public code is opened  
Then the snapshot remains readable, the reason new quotes are disabled is explained and no current catalog values replace snapshot values.

### UX-SC-011 - Privacy version changes

Given the user acknowledged an older policy version  
When submission reports a newer active version  
Then acknowledgment clears, the new resource is presented and the corrected request requires a new explicit acknowledgment.

### UX-SC-012 - Quote success boundary

Given the API persisted a quote request  
When success is presented  
Then the request code appears and the interface does not claim email delivery, staff notification, response time or a binding commercial quote.

## 18. Cross-document alignment required by this approval
