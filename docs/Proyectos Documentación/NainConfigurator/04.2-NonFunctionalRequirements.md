# Non-Functional Requirements

Document version: 1.4  
Status: Approved  
Last updated: 2026-07-28  
Scope: MVP implementation and first paying-customer operating envelope

## 1. Purpose

This document defines measurable quality requirements for the NainConfigurator shared SaaS MVP. It converts the approved commercial and user-experience model into performance, capacity, browser, renderer, availability, recovery, observability, support, maintainability and cost targets.

These values are internal engineering SLOs and acceptance thresholds. They are not contractual customer SLAs until they have been measured under production-like conditions, costed and explicitly included in a customer agreement.

Approval of this document completes Gate C and provides quantitative input to security and architecture. It does not authorize architecture, physical database design, production data or application code.

## 3. Normative measurement language

- **Must:** release-blocking requirement inside the documented supported envelope.
- **Target:** required internal SLO; a miss requires analysis and an approved exception before release.
- **P50/P75/P95/P99:** percentile across valid measured samples after the defined warm-up.
- **API latency:** server-observed elapsed time at the public application boundary, including application and data access but excluding internet latency.
- **End-to-end time:** browser-observed time including the reference network profile.
- **Availability:** successful service responses divided by eligible requests; expected business/client `4xx` responses do not count as downtime.
- **Error rate:** unexpected `5xx`, network termination or timeout produced by NainConfigurator-controlled components.
- **Sustained load:** constant load for at least 15 minutes after a 5-minute warm-up.
- **Burst load:** specified load for 60 seconds without correctness loss.

Measurements use release builds, production-equivalent configuration, representative data and no debugger. A test is invalid if tracing, caching, database size or asset delivery differs materially from the planned production path.

## 4. Reference test profiles

### 4.1 Client profiles

| Profile | Minimum test characteristics | Network profile |
|---|---|---|
| Reference desktop | 64-bit OS and browser, WebGL 2, 4 logical CPU cores, 8 GB RAM, integrated GPU from a still-supported device generation | 20 Mbps downstream, 5 Mbps upstream, 50 ms round-trip latency |
| Constrained desktop | Same platform capabilities with 4× CPU slowdown applied by the test tool | 10 Mbps downstream, 2 Mbps upstream, 100 ms round-trip latency |
| Reference mobile | Physical iOS or Android device with at least 4 GB RAM, supported current browser and WebGL 2 | 10 Mbps downstream, 2 Mbps upstream, 100 ms round-trip latency |

Lab profiles are necessary but do not replace real-user monitoring. Browser/device names and exact versions used for every release are recorded in the release test report.

### 4.2 Server and data profile

Performance tests use:

- The maximum supported product envelope from section 5.
- At least 50 companies and 500 published products in the database.
- At least 100,000 immutable configurations and 25,000 quote requests to expose index and query-shape problems.
- Realistic string lengths, catalog distribution and brand profiles rather than empty placeholder rows.
- Concurrent idempotent replays, catalog reads, validation, configuration writes and quote writes.

The exact infrastructure size is an architecture and cost decision. Passing only by using infrastructure that violates the approved cost guardrail is a failure.

### 5.1 Commercial and data scale

| Dimension | Required supported value |
|---|---:|
| Onboarded companies | 50 |
| Published products across the service | 500 |
| Published products for one company | 100 |

These values define the tested MVP envelope, not a promise of unlimited records. Publication must reject content that exceeds approved hard catalog limits rather than allowing an untested product to degrade every company.

### 5.2 Human-readable catalog content limits

| Value | Maximum Unicode scalar values |
|---|---:|
| Company display name | 150 |
| Product name | 150 |
| Product description | 2,000 |
| Price disclaimer | 500 |
| Option-group name | 150 |
| Option name | 150 |
| Compatibility-rule message | 500 |
| Managed visual or logo asset key | 200 |

The public client must wrap and present approved maximum-length content without silently truncating commercial meaning. Exact SQL Server storage units belong in `05-DatabaseDesign.md`; publication and API behavior use these logical limits.

### 5.3 Service load

| Load | Required supported value |
|---|---:|
| Concurrent active public browser sessions | 500 |
| Sustained API request rate | 50 requests/second for 15 minutes |
| Burst API request rate | 100 requests/second for 60 seconds |
| Sustained configuration creates | 10 creates/second |
| Sustained quote-request creates | 5 creates/second |
| Concurrent exact replays using the same request ID | 20 per resource intent |

An active browser session is a measurement model, not server-resident session authority. The application must preserve correctness without sticky sessions.

At twice the supported request rate, the service may miss latency targets but must not corrupt data, cross company boundaries, create duplicate resources or exhaust itself without controlled rejection. Overload behavior uses approved `429` or `503` semantics from `04.3-SecurityAndPrivacy.md`; architecture supplies the mechanism.

## 6. Public web performance

### 6.1 Core Web Vitals

Across supported mobile and desktop page views, measured separately, at least 75 percent of eligible visits must meet:

| Metric | P75 target |
|---|---:|
| Largest Contentful Paint (LCP) | ≤ 2.5 seconds |
| Interaction to Next Paint (INP) | ≤ 200 milliseconds |
| Cumulative Layout Shift (CLS) | ≤ 0.10 |

The target applies to the public experience as a whole. Delaying the renderer does not authorize a slow or unstable commercial shell.

Until enough real-user samples exist for a statistically meaningful P75, the same thresholds are release gates in the defined lab profiles. Missing field data is unknown, not a pass.

### 6.2 Commercial readiness

On the reference desktop profile with an uncached first visit:

| Experience event | P75 | P95 |
|---|---:|---:|
| Accessible shell visibly usable | ≤ 1.5 s | ≤ 2.5 s |
| Catalog controls ready after navigation | ≤ 3.0 s | ≤ 5.0 s |
| Local selection and estimate feedback | ≤ 50 ms | ≤ 100 ms |
| Authoritative validation visible after user action | ≤ 1.0 s | ≤ 2.0 s |
| Save or quote persistence result visible | ≤ 1.5 s | ≤ 3.0 s |

The constrained desktop and reference mobile profiles may take up to 1.5 times these end-to-end readiness targets, but the commercial shell must remain responsive and must never wait for 3D readiness.

### 6.3 Shell transfer budgets

| Asset group | Compressed transfer budget |
|---|---:|
| Initial HTML, CSS and application JavaScript excluding renderer | ≤ 600 KB |
| Company logo | ≤ 200 KB |
| Initial static product fallback visual | ≤ 400 KB |
| Application-owned web font transfer | 0 by default; any approved font subset is included in the 600 KB shell budget |

Third-party scripts are prohibited from bypassing these budgets. Any approved analytics or consent dependency is charged to the same shell and responsiveness targets.

## 7. Public API performance and reliability

Under sustained reference load and the maximum data profile:

| Operation | P95 API latency | P99 API latency |
|---|---:|---:|
| Get configurable product | ≤ 500 ms | ≤ 1,000 ms |
| Validate configuration | ≤ 300 ms | ≤ 750 ms |
| Create configuration | ≤ 750 ms | ≤ 1,500 ms |
| Get saved configuration | ≤ 400 ms | ≤ 1,000 ms |
| Create quote request | ≤ 750 ms | ≤ 1,500 ms |

Additional requirements:

- Unexpected API error rate remains below 0.5 percent over any 15-minute normal-load window with at least 500 eligible requests.
- Validation and read operations create no persistence side effects.
- Configuration and quote writes remain atomic through one explicit application transaction boundary and return no success until the complete aggregate is durably committed.
- Twenty concurrent exact replays return one existing resource and create no duplicate.
- A different payload reusing the same request ID remains a conflict under load.
- Synchronous blocking of I/O on public hot paths is prohibited when an asynchronous supported API exists.
- Cache failure may reduce speed but cannot change validation, pricing, ownership, version or idempotency results.

## 8. Babylon.js/WebGL quality and asset budgets

### 8.1 Renderer support boundary

Full 3D requires a 64-bit browser environment with WebGL 2 and must pass the runtime capability check. WebGPU is optional progressive enhancement, not a requirement. A nominally supported browser is not proof that one device has sufficient memory or graphics capacity.

The public client selects `Ready`, `Reduced`, `Unavailable` or `Failed` presentation from measured capability and runtime outcome. The commercial journey is always governed by section 6, even when 3D misses every target in this section.

### 8.2 Transfer and readiness budgets

| Renderer measure | Target |
|---|---:|
| Compressed renderer runtime plus initial product visual package | ≤ 30 MB |
| Total compressed 3D transfer during the normal `DESK-001` journey | ≤ 50 MB |
| One lazily loaded option asset package | ≤ 2 MB |
| First meaningful 3D visual, reference desktop | P75 ≤ 8 s; P95 ≤ 15 s |
| Capability decision or automatic fallback, reference mobile | ≤ 12 s |

The user may skip or stop renderer loading. Loading beyond the mobile limit changes the visual region to a reduced or unavailable state; it does not block controls.

### 8.3 Runtime quality

On the reference device, during a 60-second representative interaction:

- Median frame rate is at least 30 frames/second in `Ready` mode.
- P95 frame time is at most 50 milliseconds.
- Measured renderer/browser memory attributable to the experience remains below 512 MB on desktop and 384 MB on the reference mobile device.
- No continuous automatic animation runs when reduced motion is requested.
- After changing an option, the visual update begins within 200 milliseconds when the required asset is already loaded.

If the device cannot meet memory or frame targets, the client reduces quality or exits to the approved fallback. It must not repeatedly crash or reload the page.

## 9. Browser, device and accessibility support

### 9.1 Public commercial shell

At each release, the commercial shell supports and is tested on:

- Current and previous stable major versions of Chrome, Edge and Firefox on vendor-supported desktop operating systems.
- Current and previous stable major versions of Safari on vendor-supported macOS.
- Current and previous vendor-supported major iOS versions using Safari.
- Current and previous stable major Chrome versions on vendor-supported Android.

Internet Explorer, Legacy Edge, unapproved embedded WebViews, in-app social browsers and operating systems outside vendor security support are not supported. They receive a safe unsupported or degraded message when detected; no incorrect commercial behavior is allowed.

### 9.2 3D browser policy

The renderer is supported only where the selected Babylon.js release supports the browser engine and the runtime capability test passes. Mobile commercial-shell support does not promise full 3D quality. Browser support is recorded by exact version in every release report instead of hardcoding version numbers that immediately become stale.

### 9.3 Accessibility test matrix

Before a public release, the complete critical journey is manually verified with at least:

- Keyboard-only operation on current Chrome or Edge for Windows.
- NVDA with current Chrome and Firefox for Windows.
- VoiceOver with current Safari for macOS.
- VoiceOver with current Safari on iOS for the mobile commercial journey.
- 200 percent text resize and 400 percent browser zoom/reflow.
- Reduced-motion, high-contrast or forced-colors behavior where the platform exposes it.

WCAG 2.2 Level AA remains the acceptance target from `03.2-UXRequirements.md`. A renderer canvas is not exempt from the full-page requirement; equivalent product and selection information remains outside it.

## 10. Availability and service continuity

### 10.1 Internal service SLO

- Public configurator shell, required assets and API target 99.5 percent monthly availability across all hours.
- The SLO includes NainConfigurator-controlled dependencies required to load a catalog, validate, save, retrieve and persist a quote request.
- Planned maintenance may be excluded only when announced at least 72 hours earlier and totals no more than 2 hours in one calendar month.
- A release cannot advertise a contractual 99.5 percent SLA until two consecutive representative months meet the internal SLO and the support cost is approved.

The monthly 0.5 percent error budget is shared across application, database, asset delivery and NainConfigurator-controlled integrations. Moving failure to another owned component does not improve availability.

### 10.2 Degraded service

- Renderer or non-essential asset failure does not count as commercial downtime when the complete accessible fallback works.
- Failure to validate, save, retrieve or persist quote requests counts as downtime for the affected operation.
- Cached catalog presentation may serve only an approved currently published version and cannot bypass deactivation or version conflict rules.
- A dependency failure must not convert a write into an unverified success.

## 11. Recovery objectives and data durability

| Scope | Recovery point objective (RPO) | Recovery time objective (RTO) |
|---|---:|---:|
| SQL Server commercial and quote data | ≤ 15 minutes | ≤ 4 hours during the support window |
| Managed catalog and branding data | ≤ 1 hour | ≤ 4 hours during the support window |
| Reproducible 3D/static asset packages | ≤ 24 hours from approved source | ≤ 1 business day |
| Application release/configuration | Last approved release | Rollback or replacement ≤ 30 minutes |

Additional requirements:

- Backup success is monitored; an unverified backup does not satisfy the RPO.
- A restore into an isolated non-production environment is executed and evidenced at least quarterly.
- A complete service recovery exercise is executed at least twice per year before commercial scale expands.
- Restored data is checked for company ownership, idempotency uniqueness, snapshot completeness and price-component totals.
- Incidents beginning outside the human support window rely on automated recovery and monitoring; the standard MVP does not promise human 24/7 restoration. Human RTO measurement begins at the next support-window opening unless a premium agreement says otherwise.
- Retention, encryption, backup location and personal-data deletion follow `04.3-SecurityAndPrivacy.md`.

## 12. Scalability, caching and consistency

- Correctness must not depend on process memory, one application instance, sticky sessions or one renderer implementation.
- Running two application instances under the sustained-load test must preserve the same ownership, version, validation, pricing and idempotency outcomes as one instance.
- Catalog and branding cache keys include all ownership and version context required to prevent cross-company mixing.
- A product publication, deactivation or brand-profile version change becomes visible across all public nodes and controlled caches within 60 seconds.
- New writes, idempotency resolution and authoritative validation use persistence and transaction boundaries, not stale cache authority.
- Cache eviction or total cache loss may increase P95 latency temporarily but creates no incorrect response or unavailable database record.
- Scaling from 50 to 100 companies within the same per-product envelope must require capacity/configuration changes, not product-specific schema fields or code branches.

Exact caching technology, node topology, invalidation and cache-loss behavior are approved in `06-Architecture.md`.

## 13. Observability and auditability

### 13.1 Required telemetry

The system records:

- Request count, duration P50/P95/P99 and status by public operation.
- Unexpected error rate and timeout count.
- Database dependency duration and failure count.
- Catalog cache hit, miss, invalidation and age.
- Configuration and quote create success, exact replay, conflict and rollback counts.
- Renderer state distribution, load time, asset-transfer size, memory failure and fallback rate.
- Core Web Vitals split by supported device class and browser family.
- Backup success, age, restore result and recovery-test result.
- Infrastructure, storage and asset-egress cost with an attributable company/product dimension where privacy and metric cardinality allow it.

### 13.2 Trace and logging requirements

- Every API response contains a `traceId`; the same identifier correlates request, dependency and error telemetry.
- One hundred percent of unexpected failures are retained as traces; at least 10 percent of successful requests are sampled until traffic justifies a reviewed rate.
- Timestamps use UTC and structured event/message identifiers use English.
- Logs never contain full request bodies, contact email, phone, quote free text, privacy resource content or unrestricted visual-state JSON.
- Public company/product codes may be logged only when required for diagnosis; internal identifiers remain protected by the future access model.
- Quote persistence audit records outcome and non-personal reference identifiers without claiming notification.
- Log retention and operational access follow the approved security/privacy schedule and least-privilege controls.

### 13.3 Minimum alerts

| Condition | Evaluation | Required detection |
|---|---|---:|
| Public unexpected error rate ≥ 2% with at least 50 eligible requests | 5-minute window | ≤ 10 minutes |
| Any three consecutive configuration or quote persistence failures | Rolling sequence | ≤ 5 minutes |
| API P95 exceeds its operation target by 50% | 15-minute window | ≤ 20 minutes |
| No successful backup inside the approved RPO window | Continuous | ≤ 15 minutes |
| Catalog publication or deactivation not visible after 60 seconds | Publication check | ≤ 5 minutes |

Alert routing, on-call tooling and dashboards belong to `09-DeploymentAndOperations.md`.

## 14. Customer support objectives

The standard MVP support window is Monday through Friday, 09:00–18:00 Europe/Madrid, excluding Spanish national public holidays. These are internal targets until sold contractually.

| Severity | Example | Acknowledgement target | Restoration/workaround target |
|---|---|---:|---:|
| S1 Critical | Public commercial journey unavailable, configuration/quote writes failing, confirmed cross-company exposure | ≤ 1 business hour | ≤ 4 support-window hours |
| S2 High | Major degradation or one important supported browser journey blocked with fallback | ≤ 4 business hours | ≤ 2 business days |
| S3 Normal | Minor defect, visual issue with working fallback or documentation question | ≤ 1 business day | Planned and communicated |

Security or personal-data incidents follow the stricter Security S1 process in `04.3-SecurityAndPrivacy.md`. Public end-user product, sales and final-quote support remains the customer's responsibility.

## 15. Maintainability and delivery quality

### 15.1 Architecture quality constraints

- Code must follow SOLID and approved Clean Architecture/DDD boundaries.
- Domain and application behavior cannot depend on ASP.NET, SQL Server, Babylon.js, Blender, browser APIs or one notification vendor.
- Product-specific conditionals, request properties, database fields or UI screens are prohibited when adding a product inside the approved rule model.
- Shared validation and pricing behavior has one authoritative implementation reused by validate and create use cases.
- Every write use case has one explicit transaction owner; partial aggregate persistence is a release blocker.
- Public hot-path I/O is asynchronous where a supported asynchronous API exists; sync-over-async is prohibited.
- One customer's branding, assets or deployment cannot require a repository, permanent branch, schema or supported-release fork.

### 15.2 Verification thresholds

- All approved business acceptance scenarios are automated before implementation readiness is declared complete.
- Pricing, selection limits, compatibility, snapshot immutability, ownership and both idempotency scopes have 100 percent decision/branch coverage.
- Domain and application projects maintain at least 85 percent branch coverage excluding generated code.
- Critical public journeys pass contract, accessibility, supported-browser and concurrency tests.
- A test is quarantined only with an owner, reason and expiry; flaky-test rate remains below 1 percent across 50 repeated pipeline runs.
- Compiler warnings and configured static-analysis errors are zero in release builds.
- No known critical or high-severity dependency vulnerability is accepted at release without an explicit time-bounded security decision.
- Performance regression greater than 10 percent against the approved baseline blocks release unless measurements still meet every target and the regression is approved.

### 15.3 Delivery capability

- The .NET validation/test pipeline target is ≤ 10 minutes at P95.
- The complete pipeline including the renderer build and glTF/GLB validation is ≤ 15 minutes at P95.
- The same immutable release artifact is promoted between environments; customer builds are not compiled separately.
- The delivery design must support at least one safe production release per week without mandatory downtime.
- Application rollback or forward replacement meets the 30-minute recovery target; database migration safety is defined later and cannot assume destructive rollback.

Exact test tools, CI provider, branching strategy and Definition of Done belong to `08-TestingStrategy.md`, `09-DeploymentAndOperations.md` and `10-ImplementationPlan.md`.

## 16. Commercial cost guardrail

- Direct recurring infrastructure, managed-service, storage, backup, monitoring and asset-delivery cost targets at most 25 percent of recurring subscription revenue at the planned 20-customer operating point.
- The resulting target direct gross margin is at least 75 percent before onboarding labor, sales, tax and general company overhead.
- Architecture must provide a documented monthly cost model for the reference load before a provider or topology is approved.
- Cost is measured per environment and allocated per company/product where practical; one asset-heavy customer cannot remain invisible inside shared cost.
- Missing cost telemetry or a topology that meets latency only through commercially unviable overprovisioning fails this requirement.

Exact subscription price remains a commercial rate-card decision. If pricing cannot support the infrastructure required by this document, the honest choices are to change packaging, reduce the supported envelope or fund a higher-cost tier—not to hide the cost.

## 17. Personal-project implementation baseline

NainConfigurator is a personal product project. The following baseline applies when implementation begins and will be expanded in the implementation plan; no code is authorized by this section.

- Architecture selects current supported .NET, C#, Babylon.js and library versions plus one pinned Blender LTS line. An obsolete runtime or authoring line requires a recorded, time-bounded exception.
- SOLID, Clean Code and Clean Architecture are applied pragmatically; DDD boundaries are used where business complexity justifies them rather than as mandatory ceremony.
- Methods use idiomatic return types for their responsibility. `async void` remains prohibited except for unavoidable framework event callbacks that contain no business logic.
- Code identifiers, JSON property names, stable error codes, log templates and commit text use English. Localized human-readable public messages follow the approved company locale.
- Each write use case owns an explicit atomic transaction. Architecture decides whether to use a named Unit of Work abstraction or the persistence framework's native unit of work.
- Structured log templates are stable English events with redaction and `traceId`; implementation naming follows the selected platform conventions.
- Raw Postman examples show request and response JSON bodies.
- Avalisto-specific C# 7.3, naming, method, persistence, log, scoring and upload rules do not apply.

## 18. Acceptance scenarios

### NFR-SC-001 - Maximum catalog under normal load

Given the maximum product and database profile  
When sustained reference load runs for 15 minutes  
Then API P95/P99 latency, error rate and correctness meet sections 5 and 7.

### NFR-SC-002 - Renderer unavailable

Given WebGL capability fails or the 3D package exceeds its readiness limit  
When a user completes the public journey  
Then commercial web targets still apply and validation, save and quote creation remain available.

### NFR-SC-003 - Concurrent exact replay

Given one frozen valid create intent  
When 20 requests with the same request ID and canonical payload run concurrently  
Then one resource exists and every successful response resolves that same resource.

### NFR-SC-004 - Two-node correctness

Given two public application instances and no sticky session  
When reads, writes, conflicts and replays are distributed between them  
Then ownership, pricing, version and idempotency outcomes remain identical.

### NFR-SC-005 - Cache loss

Given all non-authoritative caches are empty or unavailable  
When valid public operations execute  
Then correctness remains unchanged and only documented latency degradation is allowed.

### NFR-SC-006 - Publication propagation

Given a product is published, changed or deactivated successfully  
When public nodes and controlled caches are checked  
Then the new version or unavailability is visible everywhere within 60 seconds.

### NFR-SC-007 - Browser without renderer support

Given a supported commercial-shell browser without sufficient 3D capability  
When the configurator loads  
Then it enters the approved visual fallback and the accessible commercial flow still passes.

### NFR-SC-008 - Backup restoration

Given the latest valid backup inside the RPO  
When it is restored into isolation  
Then company ownership, public-code uniqueness, idempotency, snapshots and price totals pass integrity checks.

### NFR-SC-009 - Maximum content lengths

Given published content at every approved logical length limit  
When catalog, responsive and saved-configuration views render  
Then content remains readable without silent semantic truncation and API budgets still pass.

### NFR-SC-010 - Twice-capacity overload

Given twice the supported API request rate  
When the service reaches overload  
Then no cross-company leak, partial write, duplicate resource or uncontrolled process failure occurs; excess work is rejected safely.

### NFR-SC-011 - Real-user performance

Given enough eligible field samples for supported mobile and desktop views  
When the monthly P75 is calculated  
Then LCP, INP and CLS meet their approved thresholds separately for both classes.

### NFR-SC-012 - Second-product maintainability

Given a fundamentally different product inside the supported catalog envelope  
When it is onboarded and published  
Then no schema, public DTO, business validator, screen or deployment fork is added for its product-specific dimensions.
