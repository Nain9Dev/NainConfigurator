# Security and Privacy Requirements

Document version: 1.6  
Status: Approved for architecture; real personal data remains launch-blocked  
Last updated: 2026-07-28  
Scope: Shared multi-company SaaS MVP and first paying-customer launch

## 1. Purpose

This document defines the security, privacy, tenant-isolation, abuse-prevention and personal-data lifecycle requirements for NainConfigurator. It completes the technical design portion of Gate D and is normative input to architecture, physical database design, testing and operations.

Approval authorized `06-Architecture.md` design, which is now approved. Neither document authorizes application code, physical SQL design or processing real personal data. A production launch still requires the named legal and operational artifacts in section 23.

Security claims are release requirements, not marketing claims or certifications. NainConfigurator must not claim GDPR compliance, OWASP certification, a penetration-test result or a contractual security level until the applicable evidence exists.

## 3. Normative baseline

- The public application and API must meet the applicable OWASP ASVS 5.0.0 Level 2 requirements.
- API design and verification must explicitly cover OWASP API Security Top 10 2023 risks.
- Privacy uses data minimization, purpose limitation, storage limitation, integrity, confidentiality and accountability by design.
- Security controls apply to application code, Babylon.js/WebGL assets, Blender source assets, background jobs, caches, logs, backups, administration, CI/CD and third-party services.
- Defense in depth is mandatory. A CDN, WAF, rate limiter, private network or database permission is never the only control protecting tenant or personal data.
- Failures are deny-by-default for private operations and safe-by-default for the public commercial journey.
- Production, test and development are separate trust environments. Production personal data and secrets are prohibited in lower environments.

## 4. Security surfaces and trust boundaries

The MVP has three distinct surfaces. They must not share authorization assumptions.

| Surface | Authentication | Permitted capability | Prohibited capability |
|---|---|---|---|
| Public commercial surface | None | Read published catalog, validate configuration, create/retrieve a shareable configuration and create a quote request | Read quote contact data, mutate catalog, access administration or infer another company's private state |
| Private control plane | Managed workforce identity | Approved catalog publication, privacy-resource activation, operational support, retention and incident actions according to role | Anonymous access, shared accounts, local application passwords or unrestricted production SQL |
| Service and delivery plane | Workload identity | Database, cache, storage, secret, telemetry and deployment operations required by one approved component | Interactive human use, embedded long-lived credentials or implicit cross-environment access |

Customer self-service administration and customer platform accounts remain outside the MVP. A future control plane must reuse these boundaries and must not add authorization fields to the public `Company` catalog aggregate.

## 5. Data classification

| Classification | Examples | Required treatment |
|---|---|---|
| Public | Published company, brand, product, option and privacy-resource presentation data | Integrity and availability protected; safe public caching allowed with complete tenant/version keys |
| Unlisted shareable | Saved configuration code and commercial snapshot | Accessible only with a cryptographically random code; no contact data; never accepted as authorization for private data |
| Internal commercial | Draft imports, publication evidence, support tickets, cost and non-public operational metadata | Authenticated least-privilege access; no public cache |
| Restricted personal | Quote name, email, phone, message, IP/security evidence and any support export containing them | Purpose-limited access, encryption, redaction, retention and audited deletion |
| Restricted compliance | Privacy-notice version, acknowledgment timestamp, legal-hold instruction and data-subject request evidence | Immutable or auditable as applicable; retained only for its documented purpose |
| Secret | Credentials, tokens, private keys, signing keys and database connection material | Managed secret store or workload identity only; never source, client, log or artifact content |

The service is not designed to collect special-category data, government identifiers, payment data, passwords, documents or data about criminal convictions. The quote message UI must instruct users not to include sensitive information. Accidental content remains restricted personal data; it must not be copied into telemetry or support systems.

## 6. Privacy roles and lawful-processing boundary

For quote contact data in the standard SaaS offer:

- The paying customer represented operationally by `Company` is the data controller.
- NainConfigurator is the data processor acting on documented customer instructions and under an approved data-processing agreement.
- NainConfigurator may separately be a controller for its own future billing, workforce, security and account data; those purposes and records remain outside the public product model.
- The customer owns the accuracy and legal approval of its privacy notice, declared purpose, lawful basis, rights contact and retention justification.
- NainConfigurator validates presence, version, immutability and technical publication. It does not declare the customer's lawful basis to be legally correct.

The public checkbox records that the active privacy notice was presented and acknowledged. It is not automatically consent under data-protection law, is not contractual acceptance and never grants marketing permission. The controller's approved notice must state the actual lawful basis. Marketing consent requires a separate future purpose, field, workflow and retention rule.

Before real personal data, each company requires:

- An executed customer agreement and data-processing agreement.
- Controller identity, rights contact, security contact and approved privacy notice.
- Documented lawful basis and retention value.
- Approved subprocessor list, processing regions and international-transfer position.
- An operational lead-delivery route and named incident contacts.

## 7. Threat model

### 7.1 Protected assets

- Tenant ownership and catalog integrity.
- Quote contact and free-text data.
- Immutable configuration, pricing and privacy evidence.
- Public code unpredictability and idempotency behavior.
- Administrative identities, secrets, release artifacts and audit evidence.
- Availability and cost inside the approved NFR envelope.

### 7.2 Relevant threat actors

- Anonymous bots, spammers and opportunistic internet attackers.
- A user attempting to enumerate unlisted configurations or another company's data.
- A compromised customer website or third-party script.
- A compromised dependency, build pipeline, asset or operator account.
- An authorized operator exceeding the required purpose or company scope.
- Accidental misconfiguration, cache-key omission, restore error or deletion failure.

### 7.3 Mandatory threat cases

| Threat | Required control outcome |
|---|---|
| Cross-company object access | Trusted company context, scoped queries, ownership constraints and negative isolation tests |
| Public-code enumeration | At least 96 bits of cryptographic randomness, uniform not-found behavior and rate limits |
| Quote spam and cost exhaustion | Layered endpoint/IP/company limits, idempotency, adaptive risk control and monitoring |
| Mass assignment or injection | Explicit request models, unknown-property rejection, parameterized persistence, contextual output encoding and no HTML free text |
| XSS or compromised third-party script | Restrictive CSP, controlled dependencies, no personal data in browser persistence and no arbitrary executable branding |
| SSRF or malicious resource | No server fetch of arbitrary public URLs; managed, validated asset and privacy-resource publication |
| Secret or operator compromise | Managed identity/secrets, MFA, least privilege, short sessions, rotation and audited access |
| Supply-chain compromise | Locked dependencies, scanning, SBOM, provenance and reproducible release evidence |
| Log or support leakage | Redaction by construction, no bodies, restricted access, short retention and audited exports |
| Stale backup reintroduces erased data | Encrypted finite-retention backups plus post-restore deletion reconciliation |

The threat model is reviewed before the first paying customer, annually and whenever a new public route, data category, administration capability, subprocessor or deployment model is introduced.

## 8. Company isolation

Every tenant-owned object must carry or derive an immutable internal `CompanyId`. Public identifiers never replace internal ownership.

- Company scope comes from a trusted server-side resolution or authenticated authorization context, never from an unchecked body field.
- Every read, write, cache entry, asset mapping, background job, audit event, export and retention operation includes the complete company scope required by its boundary.
- A configuration derives quote company ownership. The quote request cannot override it.
- Data-access APIs for tenant-owned aggregates require company scope by construction; an unscoped general repository is prohibited for application use.
- Database credentials use least privilege and cannot bypass application isolation for routine operation.
- Cache keys include `CompanyId` plus resource identity and applicable version. Cache values cannot be shared under a key that omits ownership.
- Storage paths and asset manifests include a non-user-controlled company partition. Public asset URLs never imply write permission.
- Background jobs enumerate explicit company partitions and are restartable without moving data between companies.
- Company deactivation blocks new public commercial actions but does not bypass retention, legal hold or deletion.

Every tenant-aware use case requires automated negative tests proving that identifiers from company A cannot read, mutate, export or delete company B data. The required pass rate is 100 percent; any failure blocks release.

## 9. Public identifiers and enumeration

- Configuration and quote codes use a cryptographically secure random generator with at least 96 bits of entropy, preserving the approved 24-hexadecimal-character random component.
- Sequential database keys, timestamps, counters, hashes of predictable data and standard non-cryptographic random generators are prohibited as public-code sources.
- Configuration codes are unlisted share capabilities for non-personal commercial snapshots only.
- Quote request codes never authorize a public read. The MVP exposes no public quote-detail or quote-list endpoint.
- Unknown, deleted, other-company and unauthorized resources use the same safe external not-found behavior where revealing the distinction creates enumeration risk.
- Error bodies contain stable codes and `traceId`, never internal keys, SQL details, stack traces, storage paths or existence hints.
- Public codes may appear in redacted operational logs. Contact data and a public code must not be logged together.

## 10. Abuse protection and request limits

Rate limits are distributed across application instances. In-process counters alone are insufficient. Limits use the best available combination of route, source IP, trusted company context and risk signal without browser fingerprinting.

### 10.1 Initial public limits

| Operation | Source limit | Company/service limit | Burst behavior |
|---|---:|---:|---|
| Published catalog GET | 120/minute/IP | 600/minute/company | 30/10 seconds/IP |
| Saved configuration GET | 60/minute/IP | 600/minute/service | 20/10 seconds/IP |
| Configuration validation POST | 60/minute/IP | 300/minute/company | 20/10 seconds/IP |
| Configuration creation POST | 20/minute/IP | 100/minute/company | 10/10 seconds/IP |
| Quote request creation POST | 20/hour/IP | 120/hour/company | 5/10 minutes/IP |

These are release defaults, not commercial plan quotas. They must be load-tested against `04.2-NonFunctionalRequirements.md`. A lower customer-specific value may be configured through approved operational data; a higher value requires capacity and abuse review, not a code fork.

### 10.2 Enforcement behavior

- Exceeded application limits return `429 Too Many Requests`, stable code `RATE_LIMIT_EXCEEDED` and a valid `Retry-After` header.
- Infrastructure overload remains a separate controlled `503` condition.
- Rejected requests create no configuration, quote, notification or partial data.
- Exact idempotent retries remain safe but still consume bounded request capacity.
- Repeated invalid JSON, oversized bodies, code enumeration, abnormal quote velocity or distributed sources trigger monitored risk events.
- A temporary block or step-up challenge must be time-bounded and must not permanently deny a shared NAT address.
- The MVP has no mandatory third-party CAPTCHA. A future challenge must be accessible, privacy-reviewed and activated adaptively rather than on every user.
- Rate limiting mitigates application abuse; it is not documented as complete DDoS protection. Edge/network protection remains an architecture requirement.

## 11. Input, output and browser security

### 11.1 Public request boundaries

| Boundary | Requirement |
|---|---|
| Media type | State-changing public routes accept only `application/json` with UTF-8 |
| Compressed request bodies | Disabled on public routes |
| Validate/create configuration body | Maximum 128 KB uncompressed |
| Create quote body | Maximum 8 KB uncompressed |
| JSON depth | Maximum 16 |
| Selected options | Maximum 500 codes, consistent with the supported catalog envelope |
| Visual state | Maximum 16 KB serialized UTF-8 under the approved schema |
| Unknown JSON properties | Rejected as malformed input rather than silently mass-assigned |

An oversized body is rejected at the earliest controlled ingress boundary with `413 Payload Too Large` and stable code `REQUEST_TOO_LARGE`. An unsupported content type returns `415 Unsupported Media Type` and `UNSUPPORTED_MEDIA_TYPE`.

### 11.2 Validation and encoding

- Validation is allowlist-based for codes, slugs, GUIDs, enums, URLs, lengths, collections and JSON schema.
- SQL access is parameterized. User or catalog text is never concatenated into a query, command, log template, header, URL or asset path.
- Quote message and catalog text are plain text. HTML, Markdown and script execution are not supported; rendering uses contextual output encoding.
- Privacy resources use HTTPS and an immutable managed publication path. The server does not fetch a customer-supplied arbitrary URL during a public request.
- Managed logos and visual assets use validated keys, not user-provided runtime URLs.
- File upload is not a public MVP capability.
- Invalid input returns bounded errors and never echoes the full offending value.

### 11.3 Browser controls

- Production uses HTTPS only. TLS 1.3 is preferred and TLS 1.2 is the minimum; older protocols are disabled.
- HSTS uses at least one year after all production subdomains are confirmed HTTPS-safe. Preload is a separate operational decision.
- CSP is deny-by-default and route-specific. Script execution is limited to approved same-origin or integrity-controlled resources. Babylon.js chunks and glTF/GLB packages are same-origin/content-addressed; no WebAssembly, worker, blob-script or cross-origin allowance is added unless a reviewed feature proves it necessary.
- `frame-ancestors` denies embedding by default. Future embedding uses an exact approved origin allowlist per company; wildcards are prohibited.
- CORS is same-origin by default. Approved cross-origin clients use an exact environment-specific allowlist; credentialed wildcard CORS is prohibited.
- `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin` and a restrictive `Permissions-Policy` are required.
- Authenticated browser state, when introduced, uses `Secure`, `HttpOnly` and appropriate `SameSite` cookies plus anti-forgery protection. Administrative tokens are never stored in browser local storage.
- Responses containing restricted data use `Cache-Control: no-store`. The public MVP currently has no response that returns quote contact data.

## 12. Administrative identity and authorization

The application must not implement or store workforce passwords.

- Private control-plane access uses a supported managed identity provider over OpenID Connect.
- Authorization Code with PKCE is required for interactive browser authentication.
- Administrative browser tokens remain server-side behind a backend-for-frontend or equivalent confidential session boundary.
- MFA is mandatory. Phishing-resistant WebAuthn/passkey or hardware-backed authentication is preferred; any fallback is documented and monitored.
- Shared accounts are prohibited. Every human action maps to one identity.
- Workloads use managed/workload identity where available. Long-lived service secrets are the exception.
- Administrative inactivity timeout is at most 30 minutes and absolute session lifetime at most 8 hours.
- Export, bulk deletion, legal hold, role change, secret access and security-policy changes require authentication no older than 15 minutes.
- Removing an operator or critical role revokes effective access within 15 minutes.
- One monitored emergency access path may exist, stored separately and tested quarterly; every use creates a critical alert.

### 12.1 Minimum authorization capabilities

| Capability | Purpose | Personal-data access |
|---|---|---|
| `CatalogPublisher` | Validate and publish company catalog, brand and immutable privacy resource | None |
| `SupportInvestigator` | Diagnose one ticket and company using redacted telemetry | None by default; time-bounded elevation for an identified quote only |
| `PrivacyOperator` | Execute approved export, erasure, retention and legal-hold instructions | Only the instructed company and records |
| `SecurityAdministrator` | Identity, security configuration and incident containment | No routine business use; incident access only |

One person may hold multiple capabilities during the small-team MVP, but permissions, reauthentication and audit events remain separate. Broad quote export and destructive bulk actions require a recorded second-person approval when a second authorized person exists; otherwise the launch risk must be explicitly accepted by the owner and customer.

Permissions are reviewed quarterly and at every role or employment change. Direct routine editing of the production database is prohibited.

## 13. Encryption, keys and secrets

### 13.1 Encryption

- All public, administrative and service traffic crossing a trust boundary is encrypted in transit.
- SQL Server data files, transaction logs, replicas and backups use encryption at rest equivalent to AES-256/TDE or a managed-service equivalent.
- Object storage, asset storage, audit storage and telemetry storage use provider encryption at rest.
- Backup encryption keys and versions remain available for the complete backup retention window and verified restore path.
- Key management is separated from encrypted data and uses least-privilege workload access.
- Production keys and secrets are isolated from non-production.

TDE is mandatory but is not treated as authorization or as protection from an already authorized database session. Application isolation, database permissions, audit and the prohibition on routine direct SQL remain required. Application-level field encryption is not mandatory for the initial low-volume contact-data MVP if these controls pass threat review; architecture must revisit it before adding special-category data, self-service search, broad exports or customer-managed database access.

### 13.2 Secret lifecycle

- Prefer workload identity and short-lived credentials over stored secrets.
- Remaining secrets reside only in a managed secret store and are injected at runtime.
- Secrets are prohibited in source control, application settings committed to the repository, browser bundles, Blender/glTF/GLB assets, logs, exception bodies, test fixtures, container images and build artifacts.
- CI scans every change and release artifact for secrets.
- Access is attributable and audited. Applications can read only their required secrets and cannot list the whole store.
- Long-lived credentials rotate at most every 90 days and immediately after suspected exposure; certificates renew before expiry.
- A confirmed exposed secret is disabled or rotated within 4 hours, with faster action for an actively exploited credential.
- Rotation is tested without requiring customer forks or data loss.

## 14. Browser data, analytics and third parties

- Quote contact values and privacy acknowledgment remain only in in-memory form state until submission and are cleared after confirmed success.
- They are prohibited from URLs, referrers, share payloads, local storage, session storage, service-worker caches, analytics and renderer state.
- Public configuration state contains no quote contact data.
- The MVP ships without advertising, behavioral profiling, session replay, cross-site tracking or non-essential analytics cookies.
- Essential security and load-balancing state must be documented, short-lived and purpose-limited.
- Aggregate product metrics use non-personal events and must not contain free text, email, phone, full IP address or unrestricted user-agent fingerprints.
- Adding a third-party script, analytics service, support widget, CAPTCHA or external notification provider requires a data-flow review, subprocessor/legal review where applicable, CSP update, retention rule and NFR budget validation.
- No production personal data is sent to generative AI, public paste services or unapproved troubleshooting tools.

## 15. Privacy-policy publication and evidence

Each `CompanyPrivacyPolicy` version is an immutable privacy-notice publication record.

- The platform stores or controls an immutable content snapshot, its SHA-256 hash, publication timestamp, public version and quote-retention value.
- `ResourceUrl` resolves to the immutable approved snapshot over HTTPS. Replacing content at the same version or URL is prohibited.
- `QuoteRetentionDays` defaults to 365, must be between 30 and 1,825 days and requires documented controller justification when greater than 365.
- Activation validates company ownership, immutable content availability, hash, rights contact, supported locale and retention value.
- Activation is atomic and audited with actor, company, old/new version, content hash, UTC timestamp and reason.
- A new active version never changes historical quote evidence and requires a new acknowledgment for a new quote request.
- The acknowledgment timestamp is generated by the server. The client timestamp is non-authoritative.
- A policy acknowledgment never implies marketing consent or proves the customer's lawful basis.

The platform checks technical completeness, not legal adequacy. Customer legal approval remains a launch prerequisite.

## 16. Retention, erasure and backup behavior

### 16.1 Retention schedule

| Data | Active retention | Disposal |
|---|---|---|
| Quote aggregate including contact, message, idempotency and acknowledgment evidence | Until `RetentionUntilUtc`, normally 365 days from creation | Hard-delete the complete quote aggregate within 24 hours unless a documented legal hold applies |
| Immutable privacy resource | While referenced plus 400 days after its final quote deletion | Delete only when no contractual or legal requirement remains |
| General application/infrastructure logs | 30 days searchable, 90 days total | Automatic deletion |
| Raw source IP in restricted security events | Maximum 30 days unless attached to an active incident | Automatic deletion or documented incident retention |
| Administrative/security audit events | 400 days | Automatic deletion unless incident/legal hold applies |
| Aggregate non-personal metrics | 13 months | Automatic deletion |
| Temporary support or rights export | Maximum 7 days | Automatic secure deletion |
| Operational backups containing personal data | Maximum 35 days | Provider/verified backup expiry |
| Security incident record | 5 years with personal data minimized | Secure deletion after legal/insurance review |

Saved configurations contain no quote contact data and remain governed by their separate commercial lifecycle. Deleting a quote does not delete or mutate its immutable configuration. If a configuration becomes personal data because another system stores an external association, that controller must disclose and govern that association.

### 16.2 Retention execution

- `RetentionUntilUtc` is computed by the server from the acknowledged policy version and persisted with the quote.
- A legal hold requires an authorized controller instruction, owner, reason, scope, start, review date and expiry or documented legal condition. Holds are reviewed at least every 90 days.
- Expiry and rights-request deletion are idempotent, company-scoped and auditable without copying deleted personal values into the audit event.
- Deletion removes contact fields, message, personal fingerprint material, quote code, client request ID and acceptance linkage as one aggregate.
- A quote idempotency guarantee ends when that quote is lawfully deleted. A later submission is a new commercial intent.
- Customer termination does not stop scheduled retention. Remaining personal data is returned or deleted within 30 days of the approved termination instruction, subject to legal hold and backup expiry.
- Deletion failures alert within 24 hours and are retried safely.

### 16.3 Backups and restoration

Selective mutation of immutable backups is not required. Instead:

- Backup retention never exceeds 35 days for stores containing quote personal data.
- Deletion instructions/tombstones required to reconcile a restored backup are stored separately, encrypted and retained at least for the backup window.
- Before a restored environment can serve production traffic, retention and rights-request deletions are reapplied and verified.
- Restore tests prove that expired or erased quote data does not reappear in active service.
- Backup copies, restore environments and exported diagnostics have the same or stricter access and regional controls as production.

## 17. Data-subject rights and customer termination

- The controller receives and verifies data-subject requests through the rights contact in its privacy notice.
- NainConfigurator does not expose a public search-by-email or self-service quote lookup.
- The platform assists the controller with access, rectification, restriction, portability and erasure instructions under the data-processing agreement.
- After a verified controller instruction, the platform produces the scoped export or completes the action within 10 business days, leaving margin for the controller's statutory response deadline.
- Exports use a common machine-readable format, are encrypted in transit, expire within 7 days and are accessible only to the authorized recipient.
- Identity verification must be proportionate; the platform must not collect more identity evidence than the request requires.
- Rectifying contact data never rewrites immutable commercial configuration or catalog history.
- Every request records controller instruction, verification outcome, scope, operator, timestamps, result and applicable refusal/legal-hold reason without duplicating the exported personal data.

## 18. Logging, audit and support access

### 18.1 Logging rules

- Logs use structured event templates with server UTC timestamp, environment, service, event code, severity, outcome and `traceId`.
- Logs never contain full request/response bodies, contact name/email/phone, quote message, privacy content, authentication token, secret, connection string or unrestricted visual-state JSON.
- User-controlled text is sanitized against log injection before any bounded diagnostic field is recorded.
- Expected validation failures use stable non-sensitive error codes rather than exception dumps.
- Production stack traces and internal exception details are restricted to protected diagnostics and never returned publicly.
- Redaction tests cover every public request model and exception path.

### 18.2 Security audit events

Audit records are append-only or tamper-evident and include:

- Unique event ID and UTC timestamp.
- Actor or workload identity and effective capability.
- Action, target type, internal non-personal target reference and company scope.
- Outcome, reason/ticket and `traceId`.
- Authentication, role change, privacy activation, catalog publication, support elevation, export, erasure, legal hold, secret access/rotation, deployment and incident events.

Audit access is itself audited. Audit events must not contain the personal values being accessed or deleted.

### 18.3 Support access

- Support starts with redacted telemetry and `traceId`.
- Viewing quote personal data requires a valid ticket, specific company and record scope, reason, time-bounded elevation no longer than 4 hours and a complete audit event.
- Bulk browsing, production copies to laptops and informal SQL queries are prohibited.
- Temporary diagnostic exports are encrypted, access-limited and deleted within 7 days.

## 19. Managed assets, dependencies and release security

- Public users cannot upload files in the MVP.
- Catalog, logo, privacy and 3D assets enter through the managed publication process.
- Publication verifies allowlisted type, declared/actual content match, size, malware scan, metadata policy, asset ownership and immutable content hash.
- SVG, HTML and other active document formats are prohibited unless architecture provides a proven sanitizer and CSP-safe delivery path. Raster formats are preferred for customer logos.
- An asset never executes with administrative origin privileges and never contains a secret or personal data.
- Dependencies and Babylon.js/.NET packages are pinned through committed lock evidence; the Blender patch/export profile and asset-license ledger are recorded release evidence.
- Every pull request runs secret, dependency and static security scanning. Every release produces a dependency inventory/SBOM and immutable artifact hashes.
- Critical/high release vulnerability behavior follows `04.2-NonFunctionalRequirements.md`. Known exploited or critical exposure requires immediate containment and a fix target within 7 calendar days; high severity within 30 days, medium within 90 and low within 180, unless a shorter vendor requirement applies.
- An independent penetration test is required before the first paying customer, annually thereafter and after a material authentication, tenancy or public-API redesign.

## 20. Incident response and security ownership

The platform names one `SecurityOwner`, one `PrivacyCoordinator` and one customer security contact before real data. The same person may initially fill platform roles, but responsibilities and escalation routes remain explicit.

### 20.1 Severity and targets

| Severity | Example | Acknowledgment | Containment target |
|---|---|---:|---:|
| Security S1 | Confirmed/suspected cross-company access, personal-data disclosure, active credential compromise | 30 minutes, 24/7 escalation | 4 hours |
| Security S2 | Exploitable high-risk weakness without evidence of compromise | 4 support hours | 2 business days |
| Security S3 | Low-risk hardening or policy deviation | 1 business day | Planned release |

Continuous automated alerting does not mean contractual 24/7 general customer support. It is a narrow internal duty for critical confidentiality and integrity events.

### 20.2 Personal-data breach process

- Preserve minimal evidence, stop further exposure, rotate affected credentials and identify companies/data categories without spreading copies.
- The processor informs the affected controller without undue delay and targets an initial notice within 24 hours after reasonably confirming a personal-data breach.
- Updates may be staged as facts become available. The controller remains responsible for supervisory-authority and data-subject notifications, including the applicable 72-hour legal assessment.
- Every incident records facts, effects, decisions, communications and remediation.
- A post-incident review and tracked corrective actions are completed within 10 business days after containment.
- The incident plan is exercised twice per year, including one cross-company or personal-data scenario.

## 21. Security verification and acceptance scenarios

### SEC-SC-001 - Cross-company catalog isolation

Given valid identifiers belonging to company A  
When they are combined with the route or trusted context of company B  
Then no A data is returned or mutated, the response reveals no private existence detail and an isolation test passes.

### SEC-SC-002 - Quote data has no public read path

Given a valid quote request code  
When an anonymous client attempts to retrieve quote details  
Then no public route returns contact, message or acknowledgment data.

### SEC-SC-003 - Enumeration resistance

Given valid-looking random configuration codes that do not exist  
When repeated requests are made inside and beyond the limit  
Then not-found behavior is uniform, rate limiting activates and no internal key or timing-based company detail is exposed.

### SEC-SC-004 - Quote abuse limit

Given five quote attempts from one source inside ten minutes  
When another attempt exceeds the burst limit  
Then the API returns `429`, `RATE_LIMIT_EXCEEDED` and `Retry-After`, and no quote or notification is created.

### SEC-SC-005 - Oversized request

Given a quote body larger than 8 KB or configuration body larger than 128 KB  
When it reaches the earliest controlled ingress  
Then it returns `413` without parsing, persistence or body logging.

### SEC-SC-006 - Stored-script attempt

Given script or HTML text in a permitted plain-text field  
When it is stored and later rendered by an authorized workflow  
Then it is displayed only as encoded text and never executes.

### SEC-SC-007 - Immutable privacy resource

Given a published privacy-policy version and content hash  
When an operator attempts to replace its content under the same version  
Then publication is rejected and the current resource remains unchanged.

### SEC-SC-008 - Retention expiry

Given a quote whose `RetentionUntilUtc` has passed and has no legal hold  
When the retention job completes  
Then the quote aggregate is absent within 24 hours and the non-personal deletion audit contains no deleted values.

### SEC-SC-009 - Restore reconciliation

Given a backup created before a verified quote erasure  
When it is restored in isolation  
Then deletion reconciliation runs before traffic and the erased quote is not available afterward.

### SEC-SC-010 - Administrative least privilege

Given a `CatalogPublisher` without privacy or security capability  
When the operator attempts export, erasure, role change or quote-data access  
Then authorization denies the action and records the attempt.

### SEC-SC-011 - Time-bounded support access

Given an approved support ticket and one quote scope  
When access is elevated  
Then it expires within four hours, cannot access another company and produces access audit evidence.

### SEC-SC-012 - Secret exposure prevention

Given a credential-like value in a proposed change or release artifact  
When CI security checks run  
Then the release is blocked and no production secret is activated from that artifact.

### SEC-SC-013 - Browser policy

Given a production response  
When headers and loaded resources are inspected  
Then HTTPS, HSTS, CSP, content-type, referrer, permissions and framing requirements pass without unauthorized third-party execution.

### SEC-SC-014 - Redaction under failure

Given a malformed quote request containing contact and message values  
When validation and an unexpected dependency failure occur  
Then public errors and protected logs contain stable codes and `traceId` but none of those personal values or the full body.

### SEC-SC-015 - Critical incident exercise

Given a simulated cross-company personal-data exposure  
When the incident runbook is exercised  
Then ownership, containment, affected-company analysis, notification decision and evidence meet section 20 targets.
